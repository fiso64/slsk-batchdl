# WebUI prototype / daemon audit

This document was re-audited from scratch against the Sockseek repository supplied on **2026-08-29** (`sockseek(20260829-072141).zip`), including the current OpenAPI document, API contracts, endpoint mappings, runtime mappers, persistence readers, and `docs/temp/cleanup-sweep-refactor-plan.md`.

Only daemon/API gaps that the **current WebUI design actually wants** are kept here. Purely frontend work, prototype-only controls, supported multi-source composition, and future deployment concerns that the prototype does not assume are intentionally omitted. “Fan-out” means the value is technically recoverable only by exhaustively paging or issuing requests per job/peer/folder/transfer, which is not a clean production source for the UI as designed.

The latest daemon cleanup establishes two important boundaries that this audit follows:

- ordinary job/workflow detail is fixed-size; descendants are traversed through cursor-paged `/api/jobs` using `parentJobId`, not recursively embedded trees;
- runtime Extract jobs are no longer a preview mechanism. A future review flow belongs in a separate short-lived, server-owned **Job Preview** resource that reuses planning semantics, remains outside runtime history, pages roots/direct children, preserves effective settings, and commits the reviewed plan without rerunning extraction.

## Search, projection, and submission

| WebUI area | Verified daemon state | Recommendation |
|---|---|---|
| **Effective search settings survive history/reprojection** | Submission can patch `DownloadSettingsPatchDto.Search`, but effective merged search settings are not returned by `JobSummaryDto` / `JobDetailDto` and are not persisted with public search history. Historical projection re-reads retained result inputs and uses the daemon’s **current** `defaultDownloadSettings.Search`; generic file fallback can synthesize `SongQueryDto(Title: metadata.Query)`. A later config/profile change can therefore change how an old search is projected. | **Persistence/API gap.** Persist a normalized effective search/projection specification with the SearchJob and expose it on detail. Historical reprojection should use that retained specification by default and accept an explicit settings-aware reprojection request when the user edits Filtering/Ranking. |
| **Generic File Search has neutral defaults** | Core `SearchSettings` defaults are music-oriented: common audio formats + length tolerance as necessary conditions and MP3/bitrate/sample-rate/strict title+album preferences. Those defaults are sensible for music jobs, but a raw generic SearchJob must currently know which defaults to neutralize. | **Backend design gap.** Give generic/raw SearchJob submission an explicit neutral file-search baseline. Track/Album paths should opt into music defaults rather than generic clients having to cancel them. |
| **Submission forms display authoritative inherited defaults** | `SubmissionOptionsDto` / `DownloadSettingsPatchDto` can express the prototype’s sparse overrides, while `ServerJobSettingsResolver` merges daemon defaults, profiles, auto-profiles, launch settings, and submission patches. `/api/profiles` exposes only `ProfileSummaryDto`; no secrets-free effective-settings projection exists. | **Defaults/introspection gap.** Add a UI-safe effective submission-defaults endpoint/projection, with enough profile-effective information for a client to show inherited values without duplicating daemon configuration logic. |
| **Filter/rank/sort the complete search result set before paging** | File/folder/aggregate projection endpoints return `SearchResultSnapshotDto<T>` containing a complete `Items` collection. Projection requests contain query/include switches only: no filter text, new settings patch, ordering, cursor, or limit. Historical projectors first materialize **all** retained `SearchProjectionInput` rows into memory and then project. | **High-priority bounded-projection gap.** Make search result projection a server-owned cursor-paged resource: apply filter/settings/grouping/order first, then page. Return projected totals and retention state with the page. This aligns search results with the daemon’s new fixed-size/bounded API direction and avoids unbounded live or historical responses. |
| **Projected folders/groups remain bounded below the top-level page** | A future top-level cursor alone would not make the current shapes bounded: `AlbumFolderDto.Files` can embed every file in a folder, while aggregate DTOs can embed every candidate/folder option in each group. A single projected item can therefore still grow arbitrarily large. | **High-priority nested-boundedness gap.** Keep folder/group summaries fixed-size with stable refs/counts/representatives. Page folder children and aggregate alternatives through separate on-demand resources. Do not solve top-level paging while retaining unlimited nested arrays. |
| **Preferred / Other result tiers are explicit** | The projector sorts candidates using necessary/preferred conditions, but result DTOs contain no tier, matched preference keys, score/reasons, or tier boundary. The WebUI can currently demonstrate Preferred only because fixtures reproduce the ranking logic. | **Projection metadata gap.** Include a stable preference tier and concise matched-preference identifiers in the paged projection result. Do not make the frontend reverse-engineer the daemon sorter. |
| **File Search projects generic directory units** | `/results/files` is a flat candidate stream. Grouping one client page cannot produce stable `(username, directoryRoot)` units, exact matching count/bytes, or best-child ordering across page boundaries. Album-folder projection is intentionally music/album-specific and is not a generic substitute. | **Backend projection gap.** Add a fixed-size generic directory summary with a stable peer+directory ref, matching count/bytes, best-child relevance metadata, retrieval completeness, and server-side ordering/paging. Load surviving root-relative children through the separately paged child resource above; derive subfolders from relative paths rather than inventing another backend identity model. |
| **File Search can retrieve the exact full generic folder** | Core `RetrieveFolderJob` already operates on generic peer-directory identity, but public `RetrieveFolderRequestDto` accepts `AlbumFolderRefDto` and `EngineSupervisor` resolves it through album-oriented projections. A raw File Search has no server-owned generic-directory ref to resolve. | **Follow-up API gap.** Generalize retrieve-folder to the proposed generic directory ref (or add an equivalent generic follow-up) while reusing `RetrieveFolderJob`. Keep generic retrieval independent of album semantics. |
| **Search peer queue depth is a result observation** | Soulseek search responses contain queue length, but `SearchProjectionInput` retains upload speed/free-slot state and discards queue length; `PeerInfoDto` consequently has no queue observation. Fetching `UserProfileDto.QueueLength` per result peer is fan-out and a later observation. | **DTO/persistence gap.** Retain queue length in `SearchProjectionInput`/search history and expose it through `PeerInfoDto` with the same observation as speed/free-slot state. |
| **Locked/private search rows are actually representable** | `SearchSession.AddResponse` increments `response.LockedFileCount` but only stores/iterates `response.Files`. Locked file rows themselves are never admitted into `rawResults`, persisted search rows, or projections. The API therefore has only a search-level locked count; adding a `locked` boolean to existing public candidates would not recover the missing identities/metadata. | **Result-retention/model gap.** If the WebUI is expected to show locked rows or exact public/locked selection counts, retain a presentation-safe locked result representation and project visibility explicitly. Otherwise the UI must treat locked files as aggregate-only and not pretend individual locked candidates exist. |
| **Album folder summaries expose authoritative projected bytes** | `AlbumFolderDto` exposes candidate identity, counts, optional files, peer data, and `IsFullyRetrieved`, but no total/matching byte aggregate. Before full retrieval, summing optional files is not authoritative. | **DTO gap.** Add projected/matching bytes to the folder summary (and, after retrieval, authoritative full-folder bytes if semantically distinct). Visibility follows the locked-result decision above rather than a separate ad-hoc field. |
| **Aggregate search has bounded group summaries + on-demand options** | `AggregateTrackCandidateDto` / `AggregateAlbumCandidateDto` expose query/item name; candidate/folder options appear only when `IncludeCandidates` / `IncludeFolders` materializes **all options for every group**. There is no stable aggregate-group ref, option/share count, representative, or per-group detail endpoint. | **DTO/overfetch gap.** Return fixed-size stable group refs with `shareCount`, `optionCount`, and the relevance-best representative in the paged aggregate summary; cursor-page one group’s ordered alternatives on demand. Folder alternatives should in turn use fixed-size folder summaries plus paged children rather than embedding every file. |
| **Selection over server-paged results stays bounded and reports resolution outcome** | Search follow-ups accept explicit file/folder refs, and file-download follow-up returns only `IReadOnlyList<JobSummaryDto>`. Once the result projection itself is cursor-paged, the current aggregate `Select all` interaction (and large generic/file selections) would otherwise require exhaustive client paging plus an arbitrarily large ref array. Missing/stale refs also have no browse-style resolution summary. | **Selection/response gap.** Bind selection to a projection revision/ref and support a bounded expression such as `only` / `all-except` (or an equivalent short-lived server selection token), then return requested/resolved/submitted/skipped/rejected counts with stable reasons. Whole-folder selection should use its folder ref rather than enumerate every child. |

## Jobs and planning

| WebUI area | Verified daemon state | Recommendation |
|---|---|---|
| **Jobs list creation time** | `PersistedJob` stores `CreatedAtUtc`, but `JobSummaryDto` / `JobDetailDto` / live `JobStateDto` do not expose it. The prototype’s relative “when” label cannot be populated after reload from the public job contract. | **DTO gap.** Expose job creation/submission time on the summary. |
| **Search-job summary counts are stable on history rows** | Live summaries can carry discovery raw/locked counts and persisted search metadata stores `ResultCount`/`LockedFileCount`, but `HistoricalJobDtoMapper.ToSummary()` intentionally writes both discovery counts as null. Distinct-peer/projected counts are not summary fields. | **DTO/semantic gap.** Define explicit summary counters (`rawResultCount`, `lockedFileCount`, and only the projected/distinct-peer counts the list truly needs) and populate them consistently for live and retained jobs. Avoid ambiguous generic “files”. |
| **Terminal Jobs history can be archived/removed** | Cancellation is advertised through `AvailableActions`, but there is no generic terminal-job archive/delete mutation. Frontend-only removal returns after reload. | **Unsupported mutation.** Add a generic terminal-job history archive/remove action with clear semantics; keep execution cancellation separate. |
| **Search again has true rerun lineage** | `SourceJobId` is explicitly provenance for independently submitted **follow-up** jobs such as downloads/retrieve-folder. Search submission cannot set it, and effective submitted search settings are not retained publicly. Using `SourceJobId` for Search Again would overload the wrong relationship. | **Rerun/persistence gap.** Add explicit rerun/clone semantics (for example a dedicated rerun endpoint or distinct `RerunOfJobId` lineage) that reuses retained effective submission/search settings. Do not repurpose `SourceJobId`. |
| **Remote CSV/List inputs are browser-uploadable** | `SubmitExtractJobRequestDto.Input` is still a string and the CSV/List extractors consume daemon filesystem paths. A browser path is meaningless unless client and daemon accidentally share a filesystem. | **Remote-input gap.** Add a bounded, expiring daemon-owned input-artifact upload resource and allow file-backed extraction/preview to reference the artifact. Define source-mutation behavior explicitly for uploaded artifacts. |
| **Optional New Job Review is a non-runtime preview** | The latest cleanup deliberately removed public `AutoStartExtractedResult` and embedded `ResultDraft`. `PrintOption.Jobs` remains the planning seam and recursively resolves extraction/job lists while stopping before normal Soulseek discovery/download. The cleanup plan explicitly calls for a future short-lived server-owned Job Preview resource with fixed-size summary/detail, paged roots/direct children, preserved effective settings, and submit-without-reresolving semantics. | **Confirmed planning API gap.** Implement that separate Job Preview resource; do not reintroduce preview state into runtime jobs. Direct Start and Review must share the same effective settings, and committing a reviewed preview must not rerun extraction or silently pick up changed defaults/source contents. |
| **Semantic job navigation survives refresh/paging** | `/api/jobs` now correctly supports roots/direct children through `parentJobId`; `JobDetailDto` is fixed-size with `ChildCount`; recursive workflow-tree DTOs/routes are gone. `ParentJobId` remains execution hierarchy, while Extract `ResultJobId` is a sibling semantic result and implementation JobList containers may appear as roots. Cursor-paged clients cannot reliably hide/flatten those roles by inspecting only the current page. | **Bounded navigation-model gap.** Keep `/api/jobs` as the traversal primitive, but expose role/relationship metadata (or a bounded semantic-root/direct-child projection) sufficient to distinguish user-submitted roots, Extract results, and implementation-only orchestration containers. Do **not** add another recursive tree API. |

## Transfers

| WebUI area | Verified daemon state | Recommendation |
|---|---|---|
| **Already-active uploads hydrate on a new WebUI connection** | `EngineStateStore.UpdateUploadTransfer()` mirrors non-queued uploads into `activeTransfers`, but upload identities have no workflow ID. `GetDaemonSnapshot()` filters `activeTransfers` to transfers whose `WorkflowId` belongs to daemon live workflows, so existing active uploads are omitted from the initial daemon snapshot. `/api/transfers/live` intentionally pages **queued uploads only**. Later state deltas can report active uploads, but a newly connected client has no bounded source for uploads that were already active. | **High-priority live-state gap.** Include active uploads in the daemon snapshot or generalize a bounded live-transfer collection to page active uploads as well as queued uploads. This is required for a correct Uploads page and Dashboard current upload throughput/count after reload/reconnect. |
| **Live download progress has parity with upload state** | Generic `TransferStateDto` supports speed, scheduling, terminal/failure fields, and advertised actions. Upload mapping populates substantially more of them; live download mapping still leaves `BytesPerSecond` (and some scheduling/action data) empty. | **Mapper/data gap.** Populate the generic live-transfer fields consistently for downloads and uploads. This also supplies the Dashboard’s current download rate without inventing a second metric source. |
| **Generic transfer rows retain optional file/audio metadata** | `TransferStateDto` / `TransferHistoryDto` expose path/bytes/status but no extension/audio facts. Download candidate targets and upload share-catalog resolution know those facts before the generic transfer projection/persistence discards them. | **DTO + persistence gap.** Add optional generic `fileMetadata` (extension, bitrate, bit depth, sample rate, length) to live and retained transfer DTOs for both directions. |
| **Downloads/Uploads have an exact bounded chronological timeline** | Live state, queued uploads, and retained transfer history are separate resources with different paging/order domains. A frontend adapter can compose small snapshots, but an exact newest-first cursor across active/queued/retained rows cannot be produced by independently paging them without merge/deduplication ambiguity at page boundaries. | **Projection gap (medium priority).** If exact chronological paging is a production requirement, add a bounded direction-filtered transfer timeline projection spanning live + queued + retained identities. Folder grouping itself stays frontend presentation and is **not** a daemon gap. |
| **Scoped bulk cancellation** | Individual transfer/job cancellation exists, but there is no atomic direction + scope (`all` / `queued` / `in-progress`) bulk action matching the shared Downloads/Uploads control. | **Unsupported mutation.** Add a generic bounded bulk-cancel contract with explicit direction/scope/filter and a resolution summary. |
| **Terminal transfer history can be archived/removed** | Retained transfer history is durable and pageable, but there is no archive/delete mutation for individual or “all completed” history entries. | **Unsupported mutation.** Add generic retained-transfer archive/delete semantics for both directions. |

## Dashboard analytics

The Dashboard should not reconstruct historical analytics from raw transfer rows. `/api/transfers?fromUtc&toUtc` filters by **transfer `CreatedAtUtc`**, not by when bytes flowed, and a transfer may span a selected range boundary. Full attempt history is separately paged per transfer. Exact range totals, bandwidth buckets, error populations, and rankings therefore need server-owned semantics rather than client-side exhaustive history scans.

| WebUI area | Verified daemon state | Recommendation |
|---|---|---|
| **Range-wide analytics: 24h / 7d / 30d / 90d / 1y / All** | No analytics endpoint exists. Retained transfer rows are cursor-paged and retention can make a range partial. There are no periodic bandwidth samples. Directional user/content/error rankings and distinct-peer counts require exhaustive grouping; attempt-failure rankings additionally require per-transfer attempt fan-out. | **High-priority aggregate gap.** Implement one bounded dashboard analytics response for the selected range, including retention completeness, summary totals, distinct peers, bandwidth buckets, directional peer rankings, content ranking, and terminal-attempt-failure ranking. |
| **Analytics byte/time semantics are explicit** | Raw transfer history cannot determine “bytes transferred during this range” for transfers that started before or finish after the boundary. Treating `CreatedAtUtc` as activity time would produce misleading totals/share ratio/rankings. | **Contract-semantics gap.** Define the analytics contract in terms of **bytes transferred during the range by direction** (and bucket those observations), or deliberately choose and document a different server-owned accounting rule. The prototype’s proposed v3 contract uses byte-activity semantics; peer counts/files and distinct peers are scoped to transfers/users with byte activity in the range, and errors are terminal attempt failures completed in the range. |

Current live transfer count is **not** a separate daemon gap: composing bounded live sources is acceptable once active-upload hydration is fixed. Daemon-health presentation is likewise a frontend composition of existing state plus client-observed API latency, not a missing backend “Healthy” boolean.

## Users / Shares and Chat

| WebUI area | Verified daemon state | Recommendation |
|---|---|---|
| **Shares global filter produces one mixed result tree + exact count** | Browse directories now support `parentId`, `query`, and `recursive`; files support `query` **within one directory**. This is a substantial improvement over the earlier audit. There is still no single mixed folder+file search over the complete browse artifact that returns matching leaves/directories with ancestor context and an exact total before pagination; finding file-name matches globally otherwise requires directory fan-out. | **Narrowed browse-projection gap.** Add a mixed browse-search projection over one browse artifact, with ancestor/path context, visibility, exact matching-file count/bytes, and cursor paging. Do not duplicate the existing directory/file browsing APIs. |
| **Chat/User actions know and mutate per-user restrictions** | `UserProfileDto` already provides presence, so Chat does not need a dedicated presence endpoint. Sockseek needs two independent inbound restrictions: upload access to this daemon's shares and incoming private messages. Neither should prevent this daemon from viewing a peer's profile/shares or sending that peer a message. | **Peer-restriction API gap.** Add one per-user resource with independent upload-access and private-message state/mutations. Chat's Block action changes only private messages; Users can expose both. Project both states into profiles and the private-message state into conversations without per-row fan-out. |

## Re-audit dispositions: deliberately removed from the gap list

The previous audit also contained several items that no longer belong in a daemon-gap document. They were checked rather than silently dropped:

- prototype scenario controls/branding are frontend-only review tooling;
- Shell Soulseek detail already comes from `SoulseekClientStatusDto.Flags`, so no extra status endpoint is needed;
- Dashboard health and client-observed API latency are presentation/composition, not a missing daemon health boolean;
- current transfer count is bounded client composition once active-upload hydration is corrected;
- transfer folder grouping is intentionally presentation over generic transfer rows;
- Chat destination-rail paging is a frontend pagination/virtualization concern because the daemon collections are already paged;
- direct-user presence is already available from `UserProfileDto`; only the two independent per-user restriction states/mutations remain a backend gap;
- a retained operational event journal may be useful later, but the current WebUI no longer requires one.

Authentication is likewise outside this audit's scope: the current prototype does not assume daemon-level authentication, so future deployment/auth work is not a present WebUI contract gap.

## Planning details that should guide the eventual backend implementation

### Job Preview

The latest cleanup plan has already made the product decision: **do not restore `AutoStartExtractedResult` or `ResultDraft` as public preview controls**. Reuse the planning semantics behind `PrintOption.Jobs` in a separate short-lived preview service. Preview summary/detail stays fixed-size, roots/direct children are cursor-paged, and selection is expressed by stable preview refs rather than round-tripping an arbitrarily large draft tree.

Effective settings belong to **preview creation**, not preview commit. A reviewed plan must preserve the settings/source resolution the user approved until Start; committing it should carry only selection (for example all-except or selected leaf refs) and must not rerun extraction. CSV/List browser inputs should use the uploaded-artifact resource above.

### Operational activity

The current live activity/state edge is intentionally ephemeral and best-effort and the prototype no longer asks for a persisted Dashboard activity feed. A retained operational event journal may still be useful in a later version for diagnostics/integrations, but it is **not a current WebUI blocker** and is therefore not part of the gap table. If introduced later, keep it separate from authoritative state/event sourcing and cursor-page a small typed/versioned payload with explicit retention; there is no reason to rename today’s live DTO merely to anticipate it.

### API refactor

`Sockseek.Api` should be split so the public wire contract and reusable remote client no longer depend on `Sockseek.Core`. Today the API project mixes DTOs/protocol types, client code, and server-side mappings back into Core settings, which means a consumer of the API surface can inherit dependencies that belong to the daemon implementation rather than to a remote client. A cleaner structure would put pure DTOs and protocol enums in a small contracts assembly, put `SockseekApiClient`, `SockseekLiveClient`, and `DaemonClientStore` in a lightweight client assembly that depends only on those contracts plus HTTP/SignalR, and keep all Core↔API mapping on the server side.

That refactor is worthwhile regardless of whether the production WebUI uses Blazor or Svelte. It gives the daemon a genuinely reusable, implementation-independent public client boundary, keeps remote CLI concerns clean, prevents accidental leakage of engine dependencies into consumers, and makes the API easier to version and test. If the WebUI is Blazor, it can reference the same browser-safe client directly; if it is Svelte, the split still provides a much clearer canonical contract and reference implementation for the TypeScript client.
