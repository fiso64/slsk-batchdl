# WebUI prototype / daemon audit

The authoritative comparison is the current C# API contracts, endpoint mappings, mappers, and persistence readers. Fully supported, clean mappings and purely frontend presentation are intentionally omitted. Proposed contracts now make several intended backend additions explicit, but do not make those daemon gaps available. "Fan-out" means the value is only recoverable by paging or issuing requests per job, peer, folder, or transfer, which is not a clean production DTO source for the prototype as drawn.

| View / component | Prototype contract | Daemon reality / production blocker | Classification / concise recommendation |
|---|---|---|---|
| **Shell - brand and scenario picker** | Permanently shows "prototype" and a Normal/Busy/Empty/Offline/Stress selector. | No daemon concept or endpoint exists for synthetic scenarios. | **Prototype-only UI.** Exact production visuals require retaining a fake control; otherwise remove it and the "prototype" label. |
| **Shell - Soulseek / daemon status** | Shows a simplified Soulseek state and labels a reachable daemon as `local`. | `ServerStatusDto` / `DaemonStateDto` expose detailed Soulseek state and readiness. No DTO says that the daemon is local; reachability is frontend transport state. | **Misleading label.** Derive online/offline client-side; do not claim `local` unless deployment configuration guarantees it. |
| **Global search - Conditions and Ranking panel / pills** | Sends necessary/preferred formats, quality, matching, length, folder structure, and peer rules; rules remain attached to each search and can later be edited. | Submission-time `DownloadSettingsPatchDto.Search` supports the shown rules. Effective conditions/ranking are not returned by `JobSummaryDto`/`JobDetailDto` and are not retained in the persisted public payload. Projection endpoints accept query hints, not a new settings patch. | **Persistence/API gap.** Persist/expose the effective search settings and add reprojection, or accept frontend-owned state plus a reimplementation of daemon matching/ranking. |
| **Dashboard - history range (24h/7d/30d/90d)** | One range drives explicitly defined buckets, rankings, errors, summaries, comparison range, and partial-retention state through `ProposedDashboardAnalyticsDto`. | No dashboard/analytics DTO or aggregate endpoint exists. Transfer history is paged and retention may make a selected range incomplete. | **Backend gap / fan-out.** Implement the proposed bounded aggregate contract. |
| **Dashboard - current Download card and sparkline** | Aggregate current download rate, active transfer-row count, queued transfer-row count, and recent rate samples. | Active rows exist, but `ToTransferState()` leaves download `BytesPerSecond` and scheduling null. No throughput samples are persisted. | **DTO/data gap.** Current download rate and sparkline still have no daemon source. |
| **Dashboard - current Upload card and sparkline** | Aggregate current upload rate/count and recent rate samples. | Live upload transfers expose speed and `UploadRuntimeStateDto` exposes active slots, but no throughput time series is stored. | **Backend data gap.** Current rate/count are derivable; sparkline is not. |
| **Dashboard - Transfers card** | Explicitly counts active, queued, and terminal transfer rows in the current snapshot. | The real bounded snapshot contains active rows, omits queued uploads, and does not retain terminal history; terminal rows require the paged history API. | **Multi-source gap.** The clarified labels still require snapshot, live upload queue, and history sources. |
| **Dashboard - bandwidth chart / chart legend** | Historical download and upload Mbps curves. | Transfer persistence keeps latest/final byte progress, not periodic bandwidth samples. | **Backend gap.** Impossible from retained DTOs even by paging all transfers. |
| **Dashboard - Downloads / Uploads user rankings** | `ProposedDashboardAnalyticsDto` defines separate top-20 directional user aggregates (bytes and distinct terminal transfer IDs) for downloads and uploads. | Raw transfer history contains directional inputs, but no bounded aggregate exists; exact top-20 rankings would require paging the entire selected range and grouping by direction + remote username in the WebUI. | **Backend gap / expensive fan-out.** Extend the proposed dashboard aggregate with separate download-user and upload-user rankings. |
| **Dashboard - Content ranking** | The proposed dashboard contract defines logical download source path as content identity. | No authoritative logical-content aggregate exists; remote-path grouping requires all history pages and remains heuristic without the proposed owner. | **Backend/model gap.** |
| **Dashboard - Errors ranking** | The proposed contract defines terminal transfer-attempt failures, count, and last-seen time. | Failure data is retained, but no aggregate exists; exact counts require paging and grouping. | **Backend gap / expensive fan-out.** |
| **Dashboard - Transfer summary / share ratio** | The proposed contract defines byte/file totals, ratio, comparison ratio, and partial retention. | Inputs are paged retained transfer history; no aggregate or ratio DTO exists. | **Backend gap / expensive fan-out.** |
| **Dashboard - Recent activity feed** | `ProposedActivityFeedItemDto` defines a durable, occurred-at-ordered download/upload/chat feed. | Activity edges are ephemeral; retained transfers and chat are separate APIs and no durable unified feed exists. | **Backend gap.** Implement the proposed feed contract. |
| **Dashboard - Daemon health panel** | One Healthy/Offline badge, Soulseek/daemon status, recent transfer-error count, and API latency. | Feature states and persistence health are exposed separately; there is no overall `Healthy` value. Error count needs history semantics, and API latency is only measurable by the frontend. | **Presentation mismatch.** Show actual feature/persistence states; label measured round-trip latency as client-observed. |
| **Search list - "when" timestamp** | Relative creation time on every row. | Creation time is stored internally, but `JobSummaryDto`, `JobDetailDto`, and `SearchStateDto` do not expose it. | **DTO gap.** Expose job creation time. |
| **Search list / result header - files, locked, peers** | File count, locked count, and distinct peer count. | Raw/locked counts exist on live summaries and persisted search metadata, but the historical job-summary mapper returns null for both, forcing a metadata request per historical search. Distinct peer count requires reading every raw result. "Files" may also mean raw hits rather than displayed projected items. | **DTO/fan-out/semantic gap.** Expose explicit raw/projected/locked/distinct-peer counts on list rows. |
| **Search list / header - Delete** | Defines Delete as an `archive-from-history` mutation with pending/success state. | No job/search delete or archive endpoint exists; browser-only removal reappears after reload. | **Unsupported backend mutation.** Implement the proposed archive mutation. |
| **Search header - Search again** | Creates a new job/search ID with `SourceJobId`, replaces the old row/URL, and clones frontend-retained rules. | New immutable submission semantics match the daemon, but current history retains both jobs and does not expose the old effective rules; a refreshed list therefore restores the superseded run. | **Persistence/list-model gap.** Expose submitted settings and add replacement/lineage semantics. |
| **Search results - filter, Conditions, Ranking, and Sort** | Each change issues `ProposedSearchResultProjectionRequestDto` over the complete retained result set before cursor pagination. | Current projection endpoints accept query hints but not filter text, a new settings patch, or explicit order; they return no preference tier. | **Unsupported exact behavior.** Add settings-aware, ordered reprojection. |
| **Search results - sort by upload speed / queue / size** | Sorts by peer upload speed, queue depth, or item size. | `PeerInfoDto` has speed and free-slot state, but no queue depth. Fetching `UserProfileDto.QueueLength` per peer is fan-out and is a different, later observation. File size exists; album total size does not. | **DTO/model gap.** Add search-response queue depth and folder total bytes, or remove those sorts. |
| **Search results - Preferred / Other tiers** | `ProposedPreferredResultDto` defines candidate tier and matched preference keys. | Daemon projections return sorted candidates but no preference classification, score, reasons, or tier boundary. | **Backend DTO gap.** Implement the proposed result metadata. |
| **Search results - PeerItemGroup** | Username, free slot, upload speed, queue length, and result count. | Username/free-slot/speed are exposed. Queue length is not. Result count is local grouping. | **DTO gap.** Extend `PeerInfoDto` with the modeled observation. |
| **Search results - track FileItemCard** | Full path, size, audio facts, and per-file Locked badge. | Path, size, bitrate/bit-depth/sample-rate/length are exposed. Per-result lock state is not; only the search-level locked-file count exists. | **DTO gap.** Add the modeled visibility/locked field. |
| **Search results - album FolderItemCard** | Cards now model retrieval state, total-vs-loaded file count, candidate identity, size, and lock fields. | `AlbumFolderDto` has optional files but no total folder bytes or lock fields. Authoritative contents still require starting/monitoring a retrieve-folder job per folder and refetching. | **Backend DTO / per-folder fan-out gap.** Implement the modeled retrieval and visibility fields. |
| **Search results - selection / Download action** | Candidate refs plus requested/public/locked/skipped counts drive disabled and partial-success presentations. | Current search DTOs do not expose per-result visibility, so those counts remain unavailable even though batch downloads themselves exist. | **Backend visibility gap.** Expose lock state and preserve the new resolution-outcome presentation. |
| **Downloads - chronological logical stream** | `ProposedLogicalDownloadTimelineItemDto` defines a dated Track/Album/RemoteFile/RemoteDirectory timeline with provenance, lifetime, detail availability, and actions. | No denormalized download-list DTO exists: job lists are summary-only, details/children require per-job requests, transfer history is file rows, and public jobs omit timestamps. | **Backend API/fan-out gap.** Implement the proposed timeline projection. |
| **Downloads - track card metadata after restart** | Remote path, peer, size, audio attributes, times, attempts, and failure remain available for completed cards. | Transfer history retains peer/path/bytes/times/attempts/failure but not audio. Historical Song payload mapping restores its query/file progress but sets the resolved candidate to null, so rich completed Track cards are not durably reconstructible. | **Persistence/DTO gap.** Persist/expose the resolved file target or simplify historical cards. |
| **Downloads - live progress, speed, ETA** | Bytes/percent, speed, ETA, and created time for active downloads. | Live download transfer projection exposes bytes only: it does not populate speed, scheduling, detailed outcome, or available actions. Created time can only be overlaid from persistence/history. | **DTO gap.** Speed and ETA cannot be rendered from current DTOs. |
| **Downloads - album card and child actions** | Folder aggregate progress/state plus every child's audio/progress/status; album and child cancellation remain available in history. | Live parent payloads and child jobs/transfers can be correlated, but require job-tree/detail fan-out. Historical Album mapping retains only aggregate directory state, not the resolved folder result/tracks; transfer history lacks audio metadata. Job cancellation is owned by advertised job actions, not the upload transfer-cancel endpoint. | **Fan-out/ownership/persistence gap.** A durable download projection is needed for this visual model. |
| **Downloads - scoped bulk Cancel** | `ProposedBulkActionRequestDto` defines current-view, direction, logical-item, and queued/in-progress scope with mutation outcomes. | The daemon exposes per-job cancellation and daemon-wide `cancel-all`, but no scoped bulk operation. | **Unsupported backend mutation.** Implement the proposed bulk contract. |
| **Downloads - Remove terminal / Remove all completed** | Archives terminal logical downloads from history with mutation state. | No job/transfer history archive or deletion endpoint exists; prototype removal is not durable. | **Unsupported backend mutation.** Implement the proposed archive semantics. |
| **Uploads - complete chronological stream** | Queued, active, and terminal uploads appear together newest-first. | Active uploads are in the daemon snapshot, queued uploads are a separately paged live queue, and terminal uploads are in paged retained history. | **Three-source merge.** Exact ordering/state requires paging and deduplication across revisions. |
| **Uploads - adjacent peer and folder projection** | Adjacent same-peer/same-parent-path files become a folder card with aggregate size/progress/speed/ETA. | Individual upload DTOs contain enough live fields to derive this, but "folder" has no daemon identity and page boundaries/late queue changes can split or reorder groups. | **Client aggregate, not authoritative.** Keep it explicitly presentational or add a server projection. |
| **Uploads - individual/folder/bulk Cancel** | Per-row actions use advertised capabilities; projected-folder and scoped bulk operations use the proposed mutation contract and show outcomes. | Individual cancellation exists. Folder/bulk cancellation still requires one request per child; no atomic/scoped bulk endpoint exists. | **Backend mutation fan-out.** Implement the proposed bulk contract. |
| **Uploads - Remove terminal / Remove all completed** | Archives terminal upload history with explicit mutation state. | No transfer-history archive/delete endpoint exists. | **Unsupported backend mutation.** Implement the proposed archive semantics. |
| **Users / Shares - global filter and match count** | `ProposedShareTreeFilterRequestDto` requests a complete-artifact mixed-tree projection with ancestor context and exact count before cursor pagination. | Directories and per-directory files are separately paged (maximum 500); query parameters do not return one mixed full-tree result. | **Backend projection gap.** Add the proposed browse-search projection. |
| **Chat - destination rails pagination** | Joined rooms and conversations show join state, previews, and unread badges. | Those facts are exposed, but both collections are paged and the prototype adds no rail pagination. | **Pagination gap.** Add load-more or virtualized destination rails. |
| **Chat - active direct-user presence / blocked label** | The selected direct thread shows presence with observation age, or locally blocked. | Conversation DTOs have no presence; a separate `UserProfileDto` request provides a later observation and can trigger several Soulseek section requests on a cold cache. The daemon exposes only aggregate blocked-user counts, no per-user read/mutate API. | **Unclean extra request + backend gap.** Add lightweight chat presence and the proposed peer-access contract. |
| **Chat - Block / Unblock user** | Uses pending/success mutation state and proposes `ProposedPeerAccessMutationDto`. | Blocked usernames remain startup peer-access configuration; no public endpoint reads or edits individual entries. Prototype state resets and cannot affect the daemon. | **Unsupported backend mutation.** Implement the proposed peer-access contract. |
